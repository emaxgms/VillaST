# DEV_NOTES.md — VillaST Developer Guide

## Project Overview

VillaST is a static website for a vacation rental villa in San Teodoro, Sardinia. It uses Firebase for backend services (Firestore, Authentication) and is deployed via Firebase Hosting.

**No build step required** — the site uses vanilla JS with ES modules loaded directly from CDN.

## Bilingual pages (two URLs, one source)

`/` is Italian, `/en/` is English. Both are static — but only `index.html` is hand-edited:

```bash
node tools/build-en.mjs     # regenerate en/index.html (run after ANY index.html edit)
node tools/check-seo.mjs    # fails if en/ drifted, a meta tag vanished, or a path is relative
```

`build-en.mjs` strips the other language's elements from the English copy, swaps
`<html lang>`, title/description/OG/JSON-LD, resolves the localized `alt`/`placeholder`
attributes (`data-alt-en`, `data-placeholder-en` are the EN twins on the Italian page), and
makes asset paths root-absolute — relative ones would resolve under `/en/` and 404.

Two things to remember when adding markup:
- new user-facing string → add both `<span class="it">` and `<span class="en">`;
- new image → add `data-alt-en` next to `alt`, then re-run the build.

## How to Verify

```bash
python3 -m http.server 8099              # then open http://127.0.0.1:8099/ and /en/
node tools/check-seo.mjs                 # structural/SEO gate, exits non-zero on drift
node test/pricing.test.mjs && node test/notify.test.mjs   # price model + email rendering
node --input-type=module --check < js/app.js   # syntax check any module

# Firestore rules suite (port 8081: 8080 is taken on this host — firebase.json "emulators")
npx -y firebase-tools@latest emulators:exec --only firestore --project demo-villast "node test/rules.test.mjs"
```

Then exercise the flow you touched in the browser: booking form, availability calendar, admin
login, gallery lightbox, sticky booking bar. There is no test framework.

## Host notifications + guest confirmation email (v4)

The admin panel is a PWA (`manifest.webmanifest` + `sw.js`, scope `/admin`): the host installs it from
Safari ("Add to Home Screen", iOS 16.4+) or Chrome, opens *Impostazioni → Attiva notifiche* (FCM token
stored in `pushTokens`) and gets one push per new booking request. The service worker is push-only and
caches nothing, so the public site is unaffected.

**One display path only.** The notifier sends a `notification` payload plus a `webpush.notification`
block (icon, badge, per-request `tag`, lang): the browser renders that block, and `sw.js` deliberately
has **no** `onBackgroundMessage`/`showNotification` — showing it there too displayed every push twice.
`notificationclick` in the SW still handles the tap (opens `/admin`).

Both push kinds and the confirmation email are sent by `tools/apps-script/notify.gs` — Google Apps
Script, time trigger every 5 minutes, service account in Script Properties, no Cloud Functions and no
paid plan. Deploy checklist and quotas: `tools/apps-script/README.md`. Flow design:
`docs/admin-panel-v4-design.md`.

### The confirmation email (flow 2)

- Trigger: the host taps *Conferma*; `js/admin.js` writes `status: 'confirmed'` in one atomic batch
  together with the availability claims. The browser sends nothing.
- Send: on the next tick, `mailConfirmed_()` queries `status == 'confirmed'` with
  `mailState != 'sent'`, skips manual bookings (`source == 'admin'`), sends from the villa Gmail via
  `MailApp` in the guest's `lang`, then writes `mailState: 'sent'` + `mailSentAt`.
- Idempotence: the `mailState` guard. A crash before the send retries on the next tick; a crash
  between send and PATCH can resend once (at-least-once).
- Content: `mailSubject_()` + `mailHtml_()` in the same file — table layout, inline styles only
  (mail clients drop `<style>` blocks). Villa facts (phone, IBAN, address, check-in 15:00 /
  check-out 10:00) are the `VILLA_` constants at the top; **replace the OWNER placeholders**.
- To change it: edit the file here, then paste the whole file over the old content in the Apps Script
  editor and Save (the trigger survives). `checkSetup()` verifies the script still sees Firestore.

Firestore rules: `reservations` (read/update/delete), `availability` (create/delete),
`pushTokens`, `pushTests` all require an `admins/{uid}` document; guests can still only create
`pending` guest requests and read `availability`. `test/rules.test.mjs` covers both sides.

## How to Add a New Public Page

1. Create a new `.html` file in the root (e.g., `guide/index.html`).
2. Copy the `<head>` and nav structure from `index.html` — including the canonical, hreflang,
   OG tags and the `jsonld` block, with the URL swapped for the new page.
3. Add a nav link in `index.html` → `<div class="nav-links">` and the mobile menu, then re-run
   `node tools/build-en.mjs` so `/en/` picks it up.
4. Add the URL to `sitemap.xml` (both language variants + alternates).
5. Test locally: `python3 -m http.server 8099`, then `node tools/check-seo.mjs`.

## How to Add a Firestore Collection

1. Define the collection schema (fields, types).
2. Add security rules in `firestore.rules`:
   ```
   match /my-collection/{doc} {
     allow read: if true;              // public read
     allow write: if request.auth != null && request.auth.token.admin == true;
   }
   ```
3. Deploy rules: `firebase deploy --only firestore:rules`
4. Add client-side code in `js/` to read/write the collection.

## Firebase Authentication

- Email/password and Google Sign-In are enabled.
- Admin access = the user has a document at `admins/{uid}` in Firestore (checked by
  `firestore.rules` via `isAdmin()`). The panel shows the uid under *Impostazioni → Account*, so the
  doc can be created once from the Firebase console.
- The Apps Script notifier authenticates as a service account (Script Properties), which bypasses
  rules — that is what lets the rules stay closed to admins only.
- `firebase.json` has an `emulators` block (firestore 8081) for the local rules suite.

## Deploying

```bash
# Full deploy (hosting + firestore rules)
firebase deploy

# Hosting only
firebase deploy --only hosting

# Firestore rules only
firebase deploy --only firestore:rules
```

## Notes

- Two languages, two URLs: Italian at `/`, English at `/en/` (generated — see above).
  The visible language is still driven by `body.lang-en` / `.lang-*` classes, which is what
  `js/reservations.js` and `js/calendar.js` read at runtime.
- Reveal-on-scroll uses the `data-aos` / `data-aos-delay` attributes but no library: `js/app.js`
  observes them with `IntersectionObserver` (the AOS dependency was removed). The hidden start
  state is scoped to `html.js`, added by an inline script in `<head>`.
- Photos are the property's own JPEGs (Booking.com exports), no CDN. `images/og-image.jpg` and
  `apple-touch-icon.png` are generated by `tools/optimize-images.py`.
- Flatpickr is used for date selection in booking forms and admin calendar, loaded from
  jsDelivr (`defer`red) — it must stay before the module scripts.
- SEO/marketing state of the site, and the owner's remaining action list:
  `docs/seo-marketing-review.md`.
